Customer Login

Requirements document · Customer Portal · Version 1.0 · Author: Product team

1. Background

The Customer Portal currently has no way for a known customer to prove who they are. Before we can build account pages, we need a small, secure login: the customer sends an email address and a password and receives a short-lived access token, which the portal then uses to call protected endpoints on their behalf.

This first release is deliberately small. There is one test customer, configured through the environment, and no sign-up. Everything in section 6 is intentionally left for later.

2. Goal

A customer with valid credentials can log in and then ask the API who they are. Anyone else is turned away with a clear, safe answer that never helps an attacker guess which accounts exist.

3. Functional requirements

3.1 Logging in

  • R1. A client logs in by sending a POST request to /api/v1/auth/login with a JSON body containing email and password.
  • R2. When the email and password are correct, the API answers 200 with a JSON body containing an access_token (a string) and a token_type whose value is bearer.
  • R3. When the email is known but the password is wrong, the API answers 401 with the body {"detail": "Invalid email or password"}.
  • R4. When the email does not belong to any customer, the API gives exactly the same 401 answer as in R3. The two cases must be impossible to tell apart from the outside, so the login cannot be used to find out which emails are registered.
  • R5. When the request body is malformed (the email is not a valid email address, or the password is empty), the API answers 422.

3.2 Using the token

  • R6. A client can call GET /api/v1/auth/me with the header Authorization: Bearer <token>. With a valid token the API answers 200 with the customer’s email: {"email": "..."}.
  • R7. If the token is missing, malformed or expired, /api/v1/auth/me answers 401.
  • R8. The login endpoint is public. The /me endpoint is the only protected endpoint in this release.

4. Data and security rules

ItemRule
EmailMust look like name@domain.tld; at most 254 characters.
PasswordBetween 1 and 128 characters.
Access tokenA signed JWT (HS256). The subject is the customer’s email. It expires 15 minutes after it is issued.
Signing keyComes from the environment variable JWT_SECRET (at least 32 characters). There must be no built-in default key: if a test customer is configured but the key is missing or too short, the application must refuse to start.
Test customerComes from the environment variables DEMO_USER_EMAIL and DEMO_USER_PASSWORD. If none is configured, every login is rejected with the answer from R3.
PasswordsNever written to logs and never returned in any response.

6. Out of scope for this release

  • Sign-up and registration, and a database table of customers.
  • Refresh tokens, “remember me” and logout.
  • Password reset and email verification.
  • Roles and permissions.
  • Rate limiting and account lockout.
  • The login screen in the web application (a separate piece of work).

7. Quality expectations

  • The login screen and API responses should feel fast to customers. (No numeric target has been agreed yet.)
  • Error messages must be understandable by a non-technical customer.

8. Open questions

  • Should the email comparison ignore upper and lower case? Product has not decided; for now treat the email exactly as typed.
